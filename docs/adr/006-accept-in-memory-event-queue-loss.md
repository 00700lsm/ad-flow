# ADR 006 - 데모에서는 이벤트 큐 유실을 감수한다

## 문제

T4-02 이후 `POST /events/*`의 201은 INSERT 완료가 아니다.
T4-03 측정: accepted=1 persistedImmediately=0 persistedAfterWait=1.
201 직후~워커 save 전에 프로세스가 끝나면 집계에 안 남는다.
Human Gate에서 내구성을 고른다.

## 201이 문제인 이유 (계약)

HTTP 201 자체는 “만들었다”는 성공 코드다. 바뀐 것은 **201의 의미**다.

```text
T4-02 이전  201 ≈ ad_events INSERT 커밋
T4-02 이후  201 ≈ 이 JVM 메모리 큐에 넣음
```

클라이언트가 201을 “디스크에 기록됨”으로 읽으면:

```text
집계 시차   201 직후 Dashboard 노출이 0일 수 있다
장애 창     성공 응답 뒤에 큐만 날아갈 수 있다
재시도      201이면 재시도하지 않는데, 디스크에는 없을 수 있다
```

코드가 틀린 것이 아니라, 성공 코드와 내구성이 어긋난 것이다.

## 현재 Context

```text
관련 Phase      4
관련 측정       T4-03 measurement.txt
현재 코드       메모리 큐 + 워커 INSERT (ADR 005)
개발자 선택     후보 A. 데모이므로 유실 감수 (2026-09-10)
```

## 검토한 대안

```text
A  유실 감수. JVM 큐 유지
B  같은 PostgreSQL에 먼저 씀 (동기 INSERT 또는 Outbox)
C  Kafka 등 브로커에 먼저 씀
```

B와 C는 둘 다 201을 “앱 힙 밖”에 맞춘다. 정본 위치만 다르다.

```text
B  정본 = 이미 쓰는 PostgreSQL
   재처리 = 남은 행을 워커가 다시 읽음
   인프라 추가 없음. POST가 다시 DB 커넥션을 씀 (T4-01과 긴장)

C  정본 = 프로세스 밖 브로커
   재처리 = Consumer가 오프셋부터 다시 읽음
   브로커·토픽·Consumer 필요. 접수와 집계 프로세스 분리
   이 저장소 측정만으로 도입하면 ROADMAP 위반
```

## 선택

대안 A.

데모 범위에서는 201 = 접수(큐)로 두고, 워커가 살아 있을 때만 집계가 따라온다.
Outbox·Kafka는 넣지 않는다. FR-11의 “장애 후 재처리”는 이 결정으로 아직 충족하지 않는다.

측정 없이 “유실이 해결됐다”고 쓰지 않는다. 코드 변경 없음.

## 결과

```text
하는 것      한계를 문서로 고정. JVM 큐 유지
하지 않는 것 Outbox, Kafka, 201 계약 변경
남은 한계    큐만 있는 동안 프로세스 종료 → 집계 유실
             워커 INSERT와 GET /ads 는 같은 DataSource
다음에 볼 때 유실이 제품 문제가 되면 B 또는 C를 다시 Human Gate
```
